## Selection

| Fork improvement | Our implementation and decision |
| --- | --- |
| Shared-region stack isolation (`5ef479a`) | Adapted explicit `noinline` boundaries for the native wrapper, SubmitGuard installer and LegacyBlend installer. Our blend workspace was already heap-backed; no second allocator or second syscall hook was added. RELEASE disassembly confirms the wrapper calls native first and calls the separate installer afterward, without a large local buffer. This is preventive stack isolation, not proof that our previous freezes had this cause. |
| Maximum-permission failure handling (`7a81e78`) | Adapted for newly allocated SubmitGuard payloads: restore current RX, set maximum RX, query both, and publish the entry only after verification. Failure frees the unpublished allocation. Existing trampolines must match payload, continuation and both RX protections. Existing cache-page maximum permissions retain our rollback policy; this does not import the fork's whole multi-page permission manager. |
| LegacyBlend gate and bulk validation (`122ce3b`) | Already covered: our Sonoma/Sequoia gate-only patch preserves the native dual-source predicate, checks a full page using bulk `memcmp`, and allocates the two-page workspace on the heap. No duplicate blend patch was imported. |
| SubmitGuard payload and rollback | Already covered: existing command-buffer payload, full-entry/payload validation, partial-write rollback and reachable-allocation retention remain. The selected change strengthens payload permission checks without replacing the payload. |
| Short VM region queries | Already present using `VM_REGION_SUBMAP_SHORT_INFO_64`; no duplicate helper module was added. |
| Sequoia shared SRD and single-engine scratch (`ac1a08e`) | Genuine missing candidate, not enabled by this migration. It replaces initialization/override functions and a 456-byte scratch function. Its blend target overlaps ours. Independent function checks and CPU simulations pass as detailed below, but the fork explicitly lists hardware display/sleep acceptance as pending. This needs its own opt-in transaction coordinated with our one existing patch owner, native compute/render comparison, and sleep/wake acceptance. More VRAM does not by itself justify changing scratch logic. |
| Video source pitch and 48-byte feedback | Already covered in our tested Sequoia encoder path and per-OS feedback tables. Retain our existing pitch regression and independent encode/readback probes. No duplicate encoder patch owner was added. |
| Eight Sequoia video swizzle consumers (`ac1a08e`) | Additional candidate beyond our current tables. Not imported together with working pitch/feedback changes: the fork's 23-record video plan combines new and existing targets and expands FairPlay behavior. CPU relocation/rollback tests alone do not verify decoded pixels for these consumers on our host. |
| Entitlement-selected PSP/FairPlay decode (`f7d3699`, `27e75c8`) | A behavior change, not equivalent to our existing FairPlay exclusion. Ours skips VDA modification for the entitlement; theirs applies an AMD decode subset while preserving AppleGVA/encode. Keep our policy for this candidate. Their own report still has black protected video on the tested Cezanne/Tahoe system. No hardware DRM improvement is claimed. |
| Native synchronization preservation (`27e75c8`) | Important if migrating SRD later. The fork no longer forces its old ImmediateSync behavior. Do not import an older SRD payload or infer that its obsolete flag/docs are current. No ImmediateSync replacement was added here. |
| Compute vtable address point | Already investigated against our installed kernel collection; the experimental hook remains disabled. Do not reactivate a kernel submit hook merely because a userspace SRD/scratch change was added upstream. |
| Laptop EC brightness | Not applicable to this HP desktop/external monitor setup. No laptop EC backend or competing display callbacks were imported. |
| Fork build system and boot controls | Keep our AppleForge/xmake packaging and current `-NRedGLFix` / VDA mode controls. Fork flags `-NRedDisplayFix`, `-NRedVideoFix` and EC controls are not aliases in our code. |

## Direct overlap and reference checks

The fork's new Sequoia references use the same cache UUID
`42EC2890-BC40-317E-BB27-45142BFF7F26` as this host. Five checked Metal functions
match their full size/hash immediately. The pipeline constructor has the same
address/size but differs because the readable cache view already contains our
`eb 0b` blend gate at cache offset `0x3087B3164`.

Changing only that known gate to stock `75 0b` in a temporary Python bytearray
reproduces the fork's entire 9428-byte constructor SHA256 exactly:
`8072175bbebd34cde337d2c00f3676c84cdc921a3069aff1ef03599bfb48b37b`.
This is an identified overlapping patch, not an unknown OS mismatch. No original
bytes were restored in host files or running processes.

A verified reader overlay of this single gate lets the fork's surface generator
reproduce its pinned generated header byte-for-byte. Its native CPU initializer
tests then pass for all six device variants. This proves reference/generator
consistency and CPU semantics; it does not submit Metal work or establish a speed
gain, compute stability or successful hardware resume.
