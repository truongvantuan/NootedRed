# AppleGVA VDA patch derivation — macOS Tahoe 26.7.1 (25G241)

Evidence backing `NootedRed/VDAGVADataTahoe.hpp`, generated by
`tools/gen_vda_gva_data.py --root /Volumes/Tahoe --cache-dir
/Volumes/Tahoe/System/Cryptexes/OS/System/Library/dyld`. Companion to
`analysis/vda-1581-gva-data.md`, which documents the 15.8.1 form.

## Source identity

- dyld shared cache UUID `31374756-89B4-34E8-A34F-56C5D57216A1`, base `0x7FF800000000`
  (cryptex location: `System/Cryptexes/OS/System/Library/dyld`; `/System/Library/dyld`
  no longer exists on Tahoe).
- AppleGVA 113.56, image UUID `CA5414F369373C059EA2D82B35AFD4F0`, image address
  `0x7FFA0C578000`.
- Selection function `AVDGetGPUAccelerators`: `0x7FFA0C59BBAC..0x7FFA0C59C01C`
  (0x470 bytes), resolved through the same three Apple log-string anchors as 15.8.1
  ("no plugin", "invalid boardId", "force AMD for flow_id"), each with a unique
  `lea` reference inside this single function.

## Control flow (Tahoe form)

Same algorithm as 15.8.1 with register reallocation (the Intel slot holder moved
from `%r15` to `%r12`; `%r15` now holds the `flow_id` argument):

- `rbp-0x130`: AMD accelerator array (unchanged offset), filled by the device
  enumeration loop at `0x...BCA9`-`0x...BD0F` with count in `r8d`.
- Both-empty guard at `0x...BD14`: `test %r14,%r14; sete %al; test %r8d,%r8d;
  sete %cl; and` — if neither the special slot nor any AMD accelerator was found,
  it logs "no plugin" and returns empty. Reaching the Intel check therefore
  guarantees (special slot != NULL) OR (AMD count > 0).
- Intel accelerator object created by `call 0x59D1BF(&rbp-0x158, &rbp-0x15C)` at
  `0x...BDC8`; then `mov -0x158(%rbp),%r12; test %r12,%r12; je 0x...BE77`.
- The `je` target `0x...BE77` logs "invalid boardId" and jumps to the shared
  epilogue `0x...BFED` (stack-canary check + return) — i.e. "no Intel
  accelerator -> return an empty list", the 15.8.1 empty-return with added logging.
- Apple's own `gvaForceAMD*` override path (`0x...BE4D`, logging "force AMD for
  flow_id") ends at `0x...BE63` with `lea -0x130(%rbp),%rsi; mov %rbx,%rdi;
  call <push_back>; jmp 0x...BFED` — insert the first collected AMD accelerator
  and return, deliberately bypassing the shared exit block `0x...BFE5`
  (`call 0x63E06C(%r12)` on the Intel object).

## Patch

| | bytes | meaning |
|---|---|---|
| site | `0x7FFA0C59BDE5` (function +0x239, page offset 0xDE5) | `je` opcode |
| find | `0F 84 8C 00 00 00` | `je 0x...BE77` (disp +0x8C), invalid-boardId empty return |
| replace | `0F 84 78 00 00 00` | `je 0x...BE63` (disp +0x78), the force-AMD insertion block |

Same-length 6-byte displacement rewrite, same shape as the shipped 15.8.1 patch.
The replacement target is Apple's own force-AMD code, not an inferred gadget.

## Verified invariants (enforced by the generator)

1. Exactly one `test %r12,%r12; je` in the function, immediately preceded by
   `mov -0x158(%rbp),%r12`.
2. The `je` target block loads the "invalid boardId" anchor string, logs it and
   ends with `jmp` to the shared epilogue.
3. The fall-through starts the board-id classification (`lea <board-id
   string>(%rip),%rsi; mov %r12,%rdi; call`).
4. The AMD insertion tail is the first `lea -0x130(%rbp),%rsi` after the
   force-AMD log reference, followed by `mov %rbx,%rdi; call; jmp`, and its
   `jmp` target equals the same epilogue as the `je` target's.
5. The epilogue begins with the stack-canary reload (`mov (%rip+x),%rax`).
6. The 6-byte find is unique inside its 4 KiB cache-file page; the page image is
   verified against the subcache file bytes.

## Residual edge case (from external review)

If the branch is taken with an empty AMD array but a non-NULL special slot
(an Intel device enumerated but its accelerator object failed to create), the
patched path pushes the uninitialised `rbp-0x130` slot. Apple's own force-AMD
path carries the same exposure (no NULL/count check at `0x...BE63`), and the
failure would be confined to the userspace process calling AppleGVA. Dynamic
LLDB confirmation of this path is scheduled as part of on-hardware validation.

## Differences vs 15.8.1

| AMD tail pattern | `4C 8B 7B 08 ...` (register copy) | `lea -0x130(%rbp),%rsi` after the force-AMD log |

## Page-cache pollution incident (2026-10-20)

While debugging an unrelated VA-layer failure on a live `-NRedVDA` boot, reads of this
cache page through the file-backed page cache returned the **patched** bytes
(`0F 84 78`) at the selection branch — looking exactly like native stock — and later
flipped back to stock (`0F 84 8C`) after the patched page was evicted.  An intermediate
"no GVA patch needed on Tahoe" conclusion drawn from those patched reads was wrong and
was retracted; the patch above stands, verified on a clean page cache by full-page
SHA-256 and `--check`.  Never derive or verify patch data from a live `-NRedVDA` boot
without the generator's committed-stock recovery path; both generators now print a
warning in that situation (`warn_if_live_patched_cache`).
